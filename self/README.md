
Конкурентность и многопоточность (Самый важный блок)

Эти задачи проверяют, насколько уверенно вы владеете горутинами, каналами, sync и context.
• Worker Pool с ограничением параллелизма и Graceful Shutdown
• Суть: Написать пул воркеров, который читает задачи из канала, обрабатывает их в N горутинах и корректно завершается по отмене контекста или закрытию входного канала, дожидаясь завершения текущих задач.
• Что проверяют: sync.WaitGroup, select, закрытие каналов без паники (send on closed channel), обработку ctx.Done().

• Параллельный обход URL / Fan-Out, Fan-In
• Суть: Дан список из 1000 URL. Нужно опросить их, делая не более 10 одновременных HTTP-запросов, собрать результаты и отменить все оставшиеся запросы, если хотя бы один вернул критическую ошибку (или если получен таймаут).
• Что проверяют: Паттерн семафора (буферизированный канал chan struct{}), errgroup (или ручную реализацию через context.WithCancel).

• Merge N отсортированных каналов (Fan-In)
• Суть: Написать функцию merge(cs ...<-chan int) <-chan int, которая объединяет данные из произвольного числа входных каналов в один выходной.
• Что проверяют: Умение запускать горутины на каждый входной канал и вовремя закрывать результирующий канал, когда все входные закрыты.

2. Структуры данных и работа с памятью

В VK высокие нагрузки, поэтому кандидатов проверяют на понимание устройства slice, map и минимизацию аллокаций.
• Потокобезопасный In-Memory Кэш с TTL (и/или LRU)
• Суть: Реализовать кэш с методами Set(key, val, ttl) и Get(key). Протухшие ключи не должны возвращаться и должны удаляться из памяти.
• Что проверяют: Выбор между sync.Mutex и sync.RWMutex, фоновую очистку (сборщик мусора), понимание, что delete из map в Go не освобождает бакеты памяти (и как это решается пересозданием мапы).
• Singleflight (Дедупликация одинаковых запросов)
• Суть: Если 100 горутин одновременно запросили данные по одному и тому же userID, в базу данных должен уйти только 1 запрос, а остальные 99 должны дождаться его результата и получить копию ответа.
• Что проверяют: Координацию горутин через каналы или sync.WaitGroup внутри мапы, защиту от гонок.

3. Алгоритмы (уровень LeetCode Easy / Medium)

В VK редко дают сложный графовый динамический код, но базовые алгоритмы на слайсы, строки и хэш-таблицы встречаются почти всегда.
• Слияние пересекающихся интервалов (Merge Intervals)
• Суть: Дан слайс временных отрезков [][]int{{1, 3}, {2, 6}, {8, 10}}. Объединить пересекающиеся в {{1, 6}, {8, 10}}.
• Что проверяют: Сортировку слайсов (slices.SortFunc), работу с индексами без выхода за границы (index out of range).
• Поиск топ-K частых элементов (Top K Frequent Elements)
• Суть: Дан лог запросов (слайс ID). Найти K самых популярных ID за линейное или \(O(N \log K)\) время.
• Что проверяют: Комбинацию map для подсчета частот и кучи (container/heap) или алгоритма Bucket Sort.
• Пересечение двух отсортированных массивов
• Суть: Найти общие элементы двух слайсов без выделения лишней памяти.
• Что проверяют: Паттерн «два указателя» (Two Pointers) и сложность O(N + M) по времени и O(1) по памяти.

4. Code Review (Поиск багов в готовом коде)

Часто на собеседовании в VK вместо написания кода с нуля показывают экран с 30–50 строками на Go и просят найти все проблемы.
Типичные ловушки, которые туда зашивают:
1. Гонка данных (Data Race): обращение к map из нескольких горутин без мьютекса (concurrent map writes).
2. Утечка горутин (Goroutine Leak): отправка в небуферизированный канал, из которого никто не читает при раннем выходе по ошибке (return err).
3. Некорректная работа со слайсами: передача слайса в функцию, где делается append (изменение исходного массива или потеря данных при реаллокации).
4. Ошибки с defer и context: вызов defer cancel() внутри бесконечного цикла for (утечка памяти до выхода из функции) или закрытие resp.Body.Close() до проверки if err != nil.

Как подготовиться эффективнее всего

На собеседовании оценивают не только рабочий код, но и ход рассуждений:
• Проговаривайте вслух граничные случаи (пустой слайс, nil, отрицательный таймаут, 0 воркеров).
• Сразу называйте сложность решения по времени и памяти (Big O).
• Не стесняйтесь сказать: «Для продакшена я бы использовал golang.org/x/sync/errgroup, но сейчас напишу реализацию на базовых примитивах».
